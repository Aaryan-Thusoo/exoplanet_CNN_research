\section{Methodology}

This section explains the full workflow and process used to develop this model. The methodology is divided into three main stages: data collection, data preparation, and model training/evaluation. Data was both synthetically generated and collected from archival Kepler sources. The collected data were then processed into fixed-length light-curve samples, labelled by class, and split into training, validation, and testing sets. Finally, a convolutional neural network was trained on the data to distinguish between confirmed exoplanet transit signals and eclipsing binary light curves. The models performance is then evaluated using classification metrics and further misclassification analysis.

To make the workflow reproducible, the project was organized as a staged pipeline. Configuration files were used to store parameters such as data paths, model settings, and evaluation choices, while DVC was used to track the order of processing stages and their outputs.

\subsection{Data Collection}

Two sets of data were used for the research in this paper. First, synthetic datasets were generated using simplified analytic light-curve shapes. This allowed us to appropriately test and check the CNN functions correctly under controlled conditions. By introducing simplistic and harder data sets the model can be evaluated solely on its set up and not by errors in the data. Afterwards, real light curve data is collected from the \textit{Kepler} mission to utilize the CNN for classification. The following subsections explain the generation and collection of all data used in this paper.

\subsubsection{Synthetic Data}

For the purpose of confirming the formed model works without error, synthetic data was made. This was developed in three stages with each being increasingly realistic. The first stage contains straight lines with only dips representing transits and eclipsing binary cases. The model is expected to come back with nearly perfect results. The generated data used randomized values for the transit or eclipsing binary dips, transit/eclipsing durations, full orbit periods all within typical ranges expected of the real life systems. Each instance contains 4894 data points which is roughly 100 days of data taking the time step to be \textit{Kepler's} cadence of 29.4 minutes. As well, the shape of dips is different for the two cases with transits having the characteristic U-shape and eclipsing binaries having the V-shape to match real data.

The second stage contains the same parameters as the initial stage but now with added noise. The noise is generated through a uniform random distribution where each data point is given a small white noise value. This creates a more difficult classification task than the first stage and tests whether the model can still identify the injected signals when handling less idealized light curves.

The final synthetic stage is the most realistic and acts as a bridge between the generated signals and observed data. Since the injected signal type is known exactly, the synthetic set is useful for testing whether the model architecture and preprocessing pipeline behave as expected. However, these synthetic data are not used as the main scientific test of the classifier; they are instead used as a control before applying the CNN to real archival light curves. \textbf{(AI)}

\subsubsection{Kepler Extraction}

The real Kepler data collection was designed to produce two labelled classes for supervised learning: confirmed transiting exoplanets and confirmed eclipsing binaries. Confirmed exoplanets were selected from the NASA Exoplanet Archive KOI cumulative table using the KOI disposition label, while eclipsing binaries required a separate catalogue of known EB targets from the Kepler Eclipsing Binary Catalog. The KepID, or Kepler Input Catalog identifier, was used as the common identifier linking catalogue labels, archive metadata, and the downloaded light curves. By first collecting the EB KepIDs, the corresponding metadata for those systems could then be queried from the NASA Exoplanet Archive. Additional metadata columns were also retained so that model errors could later be compared against physical and observational properties such as signal-to-noise ratio, transit depth, and orbital period. \textbf{(AI)}

\begin{lstlisting}[language=SQL, caption={SQL query used to extract confirmed Kepler exoplanets data from Kepler Exoplanet Archive.}, label={lst:transit-query}]
SELECT {kep_query_cols}
FROM cumulative
WHERE koi_disposition = 'CONFIRMED'
\end{lstlisting}

The name of the table is cumulative in the NASA Exoplanet Archive TAP service and so we use this naming. Finally as this is for confirmed planets only we specify the Exoplanet Archive Disposition to be "CONFIRMED".

Next the time-series data was flattened which is done to remove slow, long-term trends from the light curves while trying to preserve the shorter transit/eclipse events. This is done in the \textit{lightkurve} package by applying a Savitzky-Golay filter and dividing it out. The full \textit{Kepler} objects flux is then saved to a NumPy array.

For the light curve data we needed to split the data into three parts. A training, validation, and testing set. First we make sure there are no overlaps in the exoplanet and eclipsing binary datasets. While this should not happen it is a good precaution to make sure no data is repeated in both classes. This would damage the efficiency of the model in correctly classifying future light curves. Next, training works best when the data set of trained on exoplanets and eclipsing binaries is the same. This gives equal importance to learning the patterns in each class. Thus the data sets are made to match the size of the smaller one. Now the data is ready to be split into the different sets. However it is very important to manage how the instances are split. For one KepID, we cannot have one of its chunks in the training set, while another is in the validation or test set. This is unfair to the model as it will likely recognize the exact pattern giving a false boost in the final algorithms score. This would be a form of over fitting which would be notable in the validation results. Thus to avoid this, we split the data into the three sets not by random but by the KepIDs.

The data is set to put 80\% of the data into the training set. So in the preparation, the data takes 80\% of the KepIDs and saves them to the training set. The remaining 20\% is split in half to give 10\% to validation and 10\% to testing. Instead of taking the first 80\% of KepIDs, a shuffle function was developed which shuffles around the data while keeping the KepIDs together. This allows us to randomize which KepIDs end up being used for training, validation, and testing while maintaining the rule of keeping associated KepIDs in the same set. The randomization is set to a seed so the separation is reproducible for the exact results in this paper. 

This overall process is done to the exoplanet and eclipsing binary data sets separately to make the shuffling step more concrete. Before concatenating the two classes, the arrays of the class values needs to be made. Class 0 is the label given to all confirmed exoplanets while for eclipsing binaries they are labelled class 1. Now the training, validation, and test inputs and outputs are combined giving the completed sets of data and their outputs. Each of the three sets now properly separated are given one last shuffle to randomize the order of class 0 and class 1 inputs for the model. Once more, a set seed is used to maintain reproducibility.  

The final training, validation, and test data sets are saved separately into 3 compressed NumPy files. Each file contains the light-curve input arrays, the associated class labels, and the KepIDs needed for later error analysis.

\subsection{Model}

The model was designed to classify one-dimensional Kepler light curves into two classes: confirmed transiting exoplanets and eclipsing binaries \textbf{(AI Sentence)}. The features such as dips and repeated structures make a convolutional neural network an appropriate model for research. The CNN will scan across the time axis looking for local patterns and shapes to determine what system created the overall data. Once the networks learned filter finishes passing over the data it returns an informed estimate of whether the data comes from a potential transiting planet or an eclipsing binary. As there are only two classes, the model outputs a binary classification value with a sigmoid score converted to a 0 or 1 for transit and eclipsing binary predictions respectively.

To structure the CNN, the TensorFlow/Keras Python libraries were used. As CNNs are structured as layers, these libraries were chosen as they are simple to set up. The input layer takes in a stacked NumPy array with each of the light curves being analysed. From here each light curve is put into a one dimensional convolutional layer which runs a kernel of set size over the flux time series. The filters run through the data, learning during training and updating during back propagation. The goal of the filters is to search for local patterns in the light curve. These kernels can detect, transit/eclipse dips, ingress/egress shape, symmetry or asymmetry around dips. Multiple filters are learned and updated at once allowing the network to detect several features at a time. By utilizing multiple layers for convolution, simple features can be combined to detect more complex patterns.

Rectified Linear Units (ReLU) activations are used to introduce non-linearity which helps the model learn more complex patterns. As well ReLU activations help reduce vanishing gradients problems during the iterative learning process. After the activation function of some convolutional layers, a batch normalization layer is applied. This was used to normalize the intermediate activation results while training was going on.  Thus the next layer receives values more appropriately scaled. This was done to reduce sensitivity to learning rate decisions. The next layers are pooling which takes the largest element within a local window and saves it, discarding the rest. This lowers the computational load on the algorithm as it learns while retaining the important information. Following this a dropout layer is applied. These randomly disable some neurons in the layer during training. This is done to keep the network from relying too heavily on one path or unit. 

A global pooling layer is needed near the end of the models process in order to prepare the model for providing a result. Global pooling is a final pooling step used to reduce each feature map to its strongest response. It keeps the most strongly detected version of each learned pattern and converts them into a compact vector to prepare for the dense layers. The dense layers are meant for decision making. They combine the information from the convolutional layers and build a summary of the results. The final dense layer only has one neuron with a sigmoid activation function to produce the classification score. This score sits between 0 and 1 that is converted to a binary number. 0 is returned for transit predictions while 1 is for eclipsing binary predictions. The distance of this score from the classification threshold was used as a measure of model confidence using Equation~\ref{eq:confidence} below, where $p$ is the sigmoid classification score. A score close to either 0 or 1 was treated as high confidence, while scores close to the classification threshold of 0.5 were treated as lower confidence \textbf{(2 AI Sentences)}.

\begin{align}
    \text{confidence} = \max{(p, 1-p)}\label{eq:confidence}
\end{align}

The above information was for the training process of the CNN model. This process is repeated over several epochs with a back propagation step after each run. For the back propagation, an optimizer is required and for this paper the Adam optimizer is used. It was chosen as it is useful for adapting step sizes for different neuron weights making it more stable than more basic choices. Alongside the optimizer is the learning rate which controls how large each update step is. A choice of \textbf{(What number?)} was used to avoid too big steps and too small updates. Alongside this, a weight decay value of \textbf{(What number?)} is chosen. This value is used for regularization to discourage the model from making weights in the filter too large, preventing over-fitting.

The loss function was needed to compare the results of each training iteration with the real answers and calculating a response to how well the model did. As the classification is binary, binary cross-entropy was the chosen loss function as it works well with the sigmoid classification score. As the total training data set is large, a random selection of $32$ light curve predictions were used to determine the weight updates during back propagation. The model was trained for up to 10 epochs. Early stopping was used to monitor the validation loss during training and restore the model weights from the best validation epoch. \textbf{(2 AI Sentences)}

Upon completing the training epochs, the weights and model architecture are saved to a keras file which can be loaded and applied to any new data. As well, the history of the training is saved into a JSON file. This can then be referred back to and loaded to observe how the model performed at each epoch in its training process. Several metrics are chosen to record in the learning. Accuracy was chosen to represent how well the model does at prediction the correct class overall. As well, the loss is recorded to show if the model is making decisions with confidence or with blind guesses. Both have results recorded at each epoch for both the training data and validation data. The training results in loss are taken into account for updating the model and the validation metrics were recorded to allow for later comparison of the model's performance.

This is then split into all false positives and all false negatives to understand better the limitations of the current model. 

\subsubsection{Error Analysis}

Normal metrics tell the overall performance of the model. However, they cannot explain what information or instances are negatively affecting the model. Correct answers are not as important to focus on so the misclassified cases need to be separated out for analysis. To do so the test results are compared to the true classifications and those which do not match are saved into a compressed NumPy file. False positives are saved as instances which are predicted to be eclipsing binaries but are true confirmed exoplanet/transit samples while false negatives are for true eclipsing binaries predicted to be transits. 

Inside the saved file several columns of information are kept. First the data is split into the false positives and false negatives. Within each sub data set, the true and predicted class are recorded along with the KepID. Keeping this identifier allows for analyzing specific light curves more thoroughly. The flux data is also saved in the file for quicker access. The sigmoid score is useful as it gives the confidence value which makes it easier to understand if the model believed its prediction or was guessing. As this is binary classification it is possible for the model to guess if not sure. 

One important analysis to focus on the confidence of the model's predictions. The misclassified results were saved into subcategories of low, medium, and high confidence. As confidence can be a minimum of 0.5 and a maximum of 1.0, low-confidence cases were defined as in the 0.5 to 0.75 range, medium is between 0.75 to 0.85 and high is 0.85+. With this split now the results can be analyzed to see trends associated with systematic model errors rather than isolated mistakes. By looking over the properties of Table~\ref{tab:kep_query_cols} split by the confidence this is possible.
