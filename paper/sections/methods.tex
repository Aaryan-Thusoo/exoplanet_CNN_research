\section{Methodology}

This section explains the full workflow used to develop all models used in this paper. The methodology was divided into four main stages: data collection, data preparation, model training, and results evaluation. Data were both synthetically generated and collected from archival Kepler sources. The collected data were then processed into fixed-length light-curve samples, labelled by class, and split into training, validation, and testing sets. Finally, two convolutional neural networks were trained on the data to distinguish between confirmed exoplanet transit signals and eclipsing binary light curves. The first model was a binary classification while the second split the eclipsing binary into shallow and deep cases creating a three-class multiclass model. The performance of both models was then evaluated using classification metrics and further misclassification analysis. To act as a baseline model for comparison against the CNNs, simple random forest models were also developed. 

To make the workflow reproducible, the project was organized as a staged pipeline. Configuration files were used to store parameters such as the data paths, as well as model and evaluation settings, while DVC was used to track commands, dependencies, parameters, and outputs.

\subsection{Data Collection}

Two forms of data were used for this study. First, synthetic datasets were generated using simplified analytic light-curve shapes. This allowed for appropriate testing of the CNN architecture under controlled conditions. By introducing simple and progressively more difficult synthetic datasets the model was able to be evaluated solely on its configuration and not by observational complications. Afterwards, real light curve data was collected from the \textit{Kepler} mission to use as the main dataset for classification using the CNN. The following subsections explain the generation and collection of all data used in this work.

The real Kepler data collection was designed to produce two labelled classes for supervised learning: confirmed transiting exoplanets and confirmed eclipsing binaries (EB). Confirmed exoplanets were selected from the NASA Exoplanet Archive KOI cumulative table using the KOI disposition label, while eclipsing binaries were identified using a separate catalogue of known EB targets from the Kepler Eclipsing Binary Catalog. The KepID, or Kepler Input Catalog identifier, was used as the common identifier linking catalogue labels, archive metadata, and the downloaded light curves. By first collecting the EB KepIDs, the corresponding metadata for those systems could then be queried from the NASA Exoplanet Archive. Additional metadata columns were also retained so that model errors could later be compared against physical and observational properties such as signal-to-noise ratio, transit depth, and orbital period.

\begin{lstlisting}[language=SQL, caption={SQL query used to extract confirmed Kepler exoplanets data from Kepler Exoplanet Archive.}, label={lst:transit-query}]
SELECT {kep_query_cols}
FROM cumulative
WHERE koi_disposition = 'CONFIRMED'
AND koi_period <= 30
\end{lstlisting}

In order to collect the necessary data, a simple SQL query was used first for the confirmed exoplanets. Listed above in Listing~\ref{lst:transit-query}, this query selected the columns from the data table.  \texttt{kep\_query\_cols} contains the following columns from the Kepler archive listed in Table~\ref{tab:kep_query_cols}. The name of the table is \texttt{cumulative} in the NASA Exoplanet Archive TAP service therefore this table name was used. As this was for confirmed planets only we specify the Exoplanet Archive Disposition to be \texttt{"CONFIRMED"}. Finally, only results with periods less than or equal to 30 days were retained. This was done to make sure repeatable patterns would be more likely to appear within the fixed-length light curves used later in the pipeline.

For the eclipsing binaries, searching for rows with the disposition as "Eclipsing Binary" or "False Positive" was not sufficient. The cumulative table does not use "Eclipsing Binary" and the "False Positive" label contains multiple case scenarios not unique to EBs. In order to gather the data a second table was required. This is the Kepler Eclipsing Binaries table and it contains the KepIDs of all the EBs confirmed from the \textit{Kepler} mission. The table was read from the Kepler Eclipsing Binary Catalog webpage and after extracting the KepIDs, another SQL query was applied, written out in Listing~\ref{lst:eb-query}. The list of KepIDs is saved into \texttt{kepid\_string} and this is specified in the query to pull only the EBs and their selected metadata columns. These catalogue queries defined the labelled objects and associated metadata, while the retrieval and preprocessing of the corresponding light curves was carried out in the data preparation stage. Just like the transit dataset, the eclipsing binary dataset is limited to those with orbital periods $\leq 30$ days.

\begin{lstlisting}[language=SQL, caption={SQL query used to extract eclipsing binary information from Kepler Exoplanet Archive.}, label={lst:eb-query}]
SELECT {kep_query_cols}
FROM cumulative
WHERE kepid IN ({kepid_string})
AND koi_period <= 30
\end{lstlisting}

\subsection{Data Preparation}

The overall process of downloading and preparing each light curve was done using the \textit{lightkurve} Python package \citep{Lightkurve}. Each KepID was passed into the library to collect its flux data. As \textit{Kepler} observations are divided into quarters, multiple light-curve files can exist for a single target and thus we must stitch them all together. Next, all NaN values were removed, outliers beyond $5\sigma$ were dropped as well. In the same step the data was normalized so that flux values were placed on a common relative scale. Next, the time-series data was flattened which removed slow, long-term trends from the light curves while trying to preserve the shorter transit or eclipse events. This was done in the \textit{lightkurve} package by applying a Savitzky-Golay filter and dividing it out. The processed flux for each \textit{Kepler} object was then saved to a NumPy array.

To make the download process more manageable, the total batch was split into sub-batches of 200 KepIDs. Each sub-batch was saved into a separate CSV file until all light curves were processed. Each finalized CSV file contained two columns: the KepID and the corresponding flux sequence. It was important to keep each instance labelled with its KepID for the modelling and evaluation steps. Through the process, if a KepID did not return a usable light curve, that object was skipped and recorded separately. A KepIDs was considered unusable if \textit{lightkurve} cannot find any data to download or the collected data could not be processed following the steps in this methodology. Overall only 8 targets were skipped in the transit exoplanets list.

A total of 2131 confirmed exoplanets were pulled from the Kepler Exoplanet Archive catalogue. After preprocessing filters such as duplicate removal, missing-value removal, and period limits, 1623 KepIDs were attempted to be downloaded. This same process was then repeated for the eclipsing binaries. The initial file collected from NASA had 2878 catalogued eclipsing binaries with 2865 being used for downloads. All KepIDs were processed into sub-batches of 200 KepIDs and saved to CSV files just like the transits and include the same column data. After removing unusable downloads, the final processed sample contained 1615 confirmed exoplanet targets and 2739 catalogued eclipsing binary targets. 

For the multiclass model, an additional value was needed to separate the eclipsing binary cases into shallow and deep categories. In order to do this, the entire light curve was scanned, copied and sorted to extract the 100 smallest data points and take the median of the list. This was done to avoid outliers which could return a false dip. The median of these points was used then as an estimate of the minimum relative flux observed near the deepest part of the transit or eclipse.

After collection, the raw data and catalogue metadata needed to be converted into consistent formats suitable for the model and future evaluation. First, each input into the CNN model needed to be the same length and so the length of each model input had to be standardized. Chunking also increased the number of training instances which then raised the number of training samples available to the model. The method chosen was to split each light curve into fixed-length segments of 4894 flux measurements. Given the time step of the \textit{Kepler} mission was 29.4 minutes, this corresponds to each chunk covering a length of $\sim 100$ days. Many targets can be split into three or more of these chunks increasing the total exoplanet instances to 7596 and eclipsing binary instances to 9259. Afterwards, the chunks are saved into new CSV files, again with each containing roughly 200 total \textit{Kepler} objects. 

When preparing the model inputs, the saved flux sequences were read from the processed CSV files and converted into NumPy arrays. These arrays were then stacked so that each row represented one fixed-length light curve sample. The CNN input itself used the processed flux arrays, while the catalogue KepID was retained to link each sample back to its metadata. For the purpose of further analysis, the remaining catalogue columns in Table~\ref{tab:kep_query_cols} were retained for later analysis. 

For the multi-class version of the experiment, a threshold was required to separate the deep and shallow eclipsing binary cases. Using the binary model misclassification results and depth distribution, a practical separation was determined such that any chunk with an estimated dip $\geq 0.01$ was considered a deep eclipsing binary. The classification of shallow or deep was saved to each eclipsing binary chunk.

The calculated signal to noise estimate of each instance was also needed. While Kepler does provide the \texttt{koi\_model\_snr} column, some rows especially in the eclipsing binary cases were missing values. In order to assign an SNR estimate to as many test cases as possible, a simple formula was applied and shown in Equation~\ref{eq:snr_calc}. As this quantity was calculated directly from the available light curves, this value allowed each instance to have an assigned relative SNR estimate. NumPy was used for the standard deviation and the catalogue depth values, the result for each instance was added to the updated table. 

\begin{align}
    \text{SNR} = \frac{\text{Transit Depth}}{\text{Standard Deviation}} \label{eq:snr_calc}
\end{align}

The light curve samples were split into training, validation, and testing sets. First the datasets were checked for overlapping KepIDs in the exoplanet and eclipsing binary datasets. While this should not happen it was a good precaution to make sure no targets were repeated in both classes. This could reduce the reliability of the learned classification boundary. Next, training is most effective when the exoplanets and eclipsing binaries datasets contain the same number of instances. This gives equal importance to learning the patterns in each class. Imbalanced class sizes can bias the model toward the more prevalent case and can skew final results. Thus the data sets are made to match the same number of total Kepler targets by limiting the eclipsing binaries to the same number as the transits. This takes the eclipsing binary dataset from 9259 to 7596 instances. 

Now the data was ready to be split into the different sets. However it was very important to manage how the instances are split. For one KepID, one of its chunks could not be in the training set while another was in the validation or test set. This would be unfair to the model as it will likely recognize target-specific features giving a false boost in the final performance metrics. This would lead to data leakage and would be notable in the validation results. Thus to avoid this, we split the data into the three sets not by individual rows but by KepIDs.

The pipeline split the data using an 80/10/10 division for training, validation, and testing. Thus in preparation, the pipeline assigned 80\% of the KepIDs and saved them to the training set. The remaining 20\% was split in half to give 10\% to validation and 10\% to testing. Instead of taking the first 80\% of instances, the unique KepIDs were shuffled using a fixed random seed. This allowed randomization of which targets end up being used for training, validation, and testing while maintaining the rule of keeping associated KepIDs in the same set. 

This splitting process was done separately for the transit and eclipsing binary data giving a training, validation, and testing dataset for both classes. Before concatenating the two classes, the label arrays were created. Class 0 was the label given to all confirmed eclipsing binaries while for confirmed transits they were labelled class 1. The training, validation, and test flux arrays and class labels were combined giving the completed sets of data and their outputs. 

For the multi-class model, while all steps are the same, the eclipsing binary data was split into its shallow and deep categories. Then transits were class 0, shallow binaries were class 1 and class 2 was for the deep eclipsing binaries. The three classes were balanced by selecting the same number of transit, shallow eclipsing, and deep eclipsing KepIDs for the training, validation and testing. For both models, each of the three sets are given one last shuffle to avoid ordering the samples by class. Once more, a fixed seed was used to maintain reproducibility.  

For both the binary and multiclass models, the final training, validation, and test datasets were saved into three compressed NumPy files. Each file contains the light-curve input arrays, the associated class labels, and the KepIDs needed for later error analysis. 

\subsection{Model}

The binary CNN model was designed to classify one-dimensional Kepler light curves into two classes: confirmed transiting exoplanets and eclipsing binaries. Features such as transit or eclipse depth, dip shape, and repeated structures made a convolutional neural network (CNN) an appropriate model for this classification task. The CNN scanned across the time axis looking for local patterns and shapes to determine which class the light curve belonged to. Once the network's learned filters finished passing over the data it returned an informed estimate of whether the morphology was more consistent with a planetary transit or an eclipsing binary. As there are only two classes, the model outputs a binary classification value for transit and eclipsing binary predictions respectively.

A second multiclass version of the CNN was also trained to distinguish between shallow and deep eclipsing binaries. Using the same general architecture as the binary CNN, most layers were unchanged. The only required change was the final output layer which now gives 3 values representing the model's probability estimate for a transit, shallow eclipsing binary, and deep eclipsing binary. 

To structure the CNN, the TensorFlow/Keras Python libraries were used. As CNNs are structured as layers, these libraries were chosen because they provide a clear framework for defining sequential neural networks. Table~\ref{tab:layer_order} shows the model architecture used for the reported results. The order follows a standard one-dimensional CNN architecture.

The input layer received a stacked NumPy array with each of the light curves being analysed. From here each light curve was put into a one-dimensional convolutional layer which ran a kernel of set size over the flux time series. The learned filters were applied through the data along the time-axis, updating their weights through backpropagation during the training. The goal of the filters was to search for local patterns in the light curve. These kernels could then learn features associated with transit or eclipse dips, ingress or egress shape, as well as symmetry or asymmetry around dips. Multiple filters are learned and updated at once allowing the network to detect several features at a time. By utilizing multiple layers for convolution, simple features can be combined to detect more complex patterns.

After the convolution layer, a batch normalization layer was applied. This standardized the intermediate results during training. This helped the next layer received values more appropriately scaled. After the batch normalization, an activation function was applied to the data. Rectified Linear Units (ReLU) activations were chosen as they introduce non-linearity which helped the model learn more complex patterns. In addition, ReLU activations helped reduce vanishing gradient effects during the iterative learning process. This was done to reduce sensitivity to learning rate decisions. The next layers were Max-pooling which took the largest element within a local window and retained it while discarding the rest. This lowered the computational load on the algorithm as it learned while retaining the strongest local responses. Following this a dropout layer was applied. These set a random fraction of activations to zero during training and reactivated them during evaluation. This was done to keep the network from relying too heavily on one path or unit. 

A final pooling layer was needed near the end of the network in order to convert the learned feature maps into a compact representation. Global pooling was then used to reduce each feature map by keeping the most strongly detected version of each learned pattern and converted them into a compact vector to prepare for the dense layers. The dense layers combined the information from the convolutional layers and learned combinations of features that separate the two classes. The final dense layer was chosen based on the type of model being trained. For the binary case, this output layer contained one neuron with a sigmoid activation function to produce the classification score. This score lies between 0 and 1 which was then converted to a binary number. Scores below the threshold returned 0 for eclipsing binary predictions while any scores above it assigned 1 for transiting exoplanet predictions. The distance of this score from the classification threshold was used as a measure of binary models confidence using Equation~\ref{eq:bi_confidence} below, where $p$ is the sigmoid classification score. 

\begin{align}
     \text{C}_{\text{binary}} = \max{(p, 1-p)}\label{eq:bi_confidence}
\end{align}

For the multiclass case, there were three output neurons with each representing one of the three classes. The activation chosen was softmax which gives a probability for each class, and the loss function was sparse categorical cross-entropy. As the labels are given as 0, 1, 2 and not as one-hot vectors, this was the appropriate choice for classifying our results. The predicted class is the class with the largest softmax probability. The confidence value is defined as the output neuron with the largest recorded probability. Equation~\ref{eq:mc_confidence} below shows the simple confidence function used for the multiclass model where $p_0$, $p_1$, and $p_2$ are the softmax probabilities of each class

\begin{align}
    \text{C}_{\text{multiclass}} = \max{(p_0, p_1, p_2)}\label{eq:mc_confidence}
\end{align}

The above training process was repeated over several epochs with a backpropagation step after each mini-batch. For the backpropagation, the Adam optimizer was used. Adam was chosen as it adjusts update sizes for different network weights making it more stable than standard gradient descent. Alongside the optimizer was the learning rate which controlled how large each update step was. A choice of 0.005 was used to avoid too big steps and too small updates. Alongside this, a weight decay value of 0.001 was chosen. This value was used for regularization to discourage overly large weights throughout the model, preventing over-fitting.

The loss function was needed to compare the results of each training iteration with the true labels and measures the difference between predicted scores and true labels. As the classification was binary, binary cross-entropy was the chosen loss function as it is appropriate for the sigmoid classification score. For the multiclass CNN, sparse categorical cross-entropy was used instead because labels were stored as integer values. For both models, as the total training dataset was large, a random selection of $32$ light curve samples were used to determine the weight updates during backpropagation. The model was trained for up to 30 epochs. Early stopping was used to monitor the validation loss during training and restore the model weights from the best validation epoch.

After training, the weights and model architecture were saved to a \texttt{.keras} model file which can be loaded and applied to validation or test light curves prepared in the same format. Additionally, the history of the training was saved into a JSON file. This can then be used to inspect how the model performed at each epoch in its training process. Several metrics were chosen to record in the learning process. Accuracy was recorded as the fraction of correctly classified samples. As well, the loss was recorded to show the prediction error during training. The accuracy and loss results were recorded at each epoch for both the training data and validation data. The training loss results were taken into account for updating the model and the validation metrics were recorded to allow for later monitoring generalization during the model's training.

Several other metrics were recorded after training. The finalized models were evaluated on the test set. The binary model saved holding the accuracy, precision, recall, F1 score, and ROC AUC. For the multiclass model, the accuracy, macro averaged precision, recall, and F1 score were saved. These results can then be used to asses more concretely what the model was good at and where it struggles.

\subsubsection{Random Forest Model}

To provide a comparison to the CNN model, a random forest model was used. It serves as a baseline and simpler process which helps to test whether the CNN is learning extra time-series shape information. The random forest did not use the full light curve arrays directly but instead used features of the individual chunks. From the chunk data, the mean, standard deviation, minimum, and maximum of the flux data were extracted as input features. As well the estimated chunk depth was added to the observed features. Metadata from the Kepler archive were not applied to the model as this info comes from processed data and would not be a fair comparison to the CNN. The exact same set up was set up for the multiclass case.

This model was trained where the prepared training and validation sets were combined to become the full training set with the test set being kept untouched. The same metrics as the convolutional neural network were collected and used for later comparison between the two models. This process was also applied to the multiclass case. In both random forest models a total of 300 estimators were used to reach the results.


\subsubsection{Error Analysis}

To further analyse the CNN, all misclassified light curves needed to be separated from the overall test set. Their KepID, flux input array, true class, predicted class, and confidence value calculated from the sigmoid score were saved. The misclassified instances were then split into all false positives and all false negatives to better understand the limitations of the current model. Standard classification metrics quantify the overall performance of the model. However, they cannot explain which properties or examples the model misclassified. Thus, the incorrect results needed to be saved into a separate dataset. To do so the test results were compared to the true classifications and those which did not match were saved into a compressed NumPy file. For the binary model, false positives were saved as instances which were predicted to be transits but are labelled eclipsing binaries samples while false negatives were for true transits predicted to be eclipsing binaries. 

The confidence value makes it easier to understand if the model output was close to or far from the classification threshold. For the binary classification, there is a clear uncertainty point at $0.5$. The closer a sigmoid score output is to this threshold, the less confident the model was in its prediction. In the multiclass case, the model instead has problems when two or more neurons have similar softmax scores. The minimum confidence is closer to $1/3$ so while the class with the largest probability will be selected, the model would be less confident in its decision.

The misclassified results were grouped into categories of low, medium, and high confidence. Since binary confidence ranges can be a minimum of 0.5 and a maximum of 1.0, low-confidence cases were defined as in the 0.5 to 0.75 range, medium was between 0.75 to 0.85 and high was greater than or equal to $0.85$. Using this split, the results can be analysed to see trends associated with systematic model errors rather than isolated mistakes. By looking over the properties of Table~\ref{tab:kep_query_cols} split by the confidence this was possible. A similar confidence analysis was also applied to the multiclass model. Since the multiclass model has three possible outputs, low-confidence predictions occur when the class probabilities are similar, while high-confidence mistakes indicate cases where the model strongly favoured the wrong class.
