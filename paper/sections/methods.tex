\section{Methodology}

This section explains the full workflow used to develop this model. The methodology was divided into four main stages: data collection, data preparation, model training, and results evaluation. Data were both synthetically generated and collected from archival Kepler sources. The collected data were then processed into fixed-length light-curve samples, labelled by class, and split into training, validation, and testing sets. Finally, two convolutional neural networks were trained on the data to distinguish between confirmed exoplanet transit signals and eclipsing binary light curves. The first model was a binary classification while the second splits the eclipsing binary into shallow and deep cases creating a 3-way multi-class model. The performance of both models were then evaluated using classification metrics and further misclassification analysis. To act as a baseline model for comparison against the CNNs, simple random forest models were also developed.

To make the workflow reproducible, the project was organized as a staged pipeline. Configuration files were used to store parameters such as data paths, model settings, and evaluation settings, while DVC was used to track the order of processing stages and their outputs.

\subsection{Data Collection}

Two forms of data were used for the research in this paper. First, synthetic datasets were generated using simplified analytic light-curve shapes. This allowed for appropriate testing of the CNN functions under controlled conditions. By introducing simplistic and harder data sets the model was able to be evaluated solely on its set up and not by errors in the data. Afterwards, real light curve data was collected from the \textit{Kepler} mission to use the CNN for classification. The following subsections explain the generation and collection of all data used in this paper.

\subsubsection{Synthetic Data}

Synthetic data were used to check that the model architecture and training pipeline behaved as expected under controlled conditions. The synthetic data were developed in three stages with each being increasingly realistic. The first stage contains straight lines with only dips representing transits and eclipsing binary cases. This stage was expected to come back with nearly perfect results. The generated data used randomized values for the transit or eclipsing binary dips, transit or eclipse durations, orbital periods all within typical ranges expected of the real systems. Each instance contains 4894 data points which is roughly 100 days of data assuming the \textit{Kepler} long-cadence of 29.4 minutes. In addition, the shape of dips is different for the two cases with transits having the characteristic U-shape and eclipsing binaries having the V-shape to match real data.

The second stage used the same underlying signal parameters as the initial stage but added noise to each light curve. The noise was generated through a uniform random distribution where each data point was perturbed by a small white noise value. This creates a more difficult classification task than the first stage and tests whether the model can still identify the injected signals when handling less idealized light curves.

The final synthetic stage was the most realistic of the three and acts as a bridge between the generated signals and observed data. Since the injected signal type was known exactly, the synthetic set was useful for testing whether the model architecture and preprocessing pipeline behave as expected. However, these synthetic datasets are not used as the main scientific test of the classifier. Instead, they are used as a control before applying the CNN to real archival light curves. 

\subsubsection{Kepler Extraction}

The real Kepler data collection was designed to produce two labelled classes for supervised learning: confirmed transiting exoplanets and confirmed eclipsing binaries. Confirmed exoplanets were selected from the NASA Exoplanet Archive KOI cumulative table using the KOI disposition label, while eclipsing binaries were identified using a separate catalogue of known EB targets from the Kepler Eclipsing Binary Catalog. The KepID, or Kepler Input Catalog identifier, was used as the common identifier linking catalogue labels, archive metadata, and the downloaded light curves. By first collecting the EB KepIDs, the corresponding metadata for those systems could then be queried from the NASA Exoplanet Archive. Additional metadata columns were also retained so that model errors could later be compared against physical and observational properties such as signal-to-noise ratio, transit depth, and orbital period.

\begin{lstlisting}[language=SQL, caption={SQL query used to extract confirmed Kepler exoplanets data from Kepler Exoplanet Archive.}, label={lst:transit-query}]
SELECT {kep_query_cols}
FROM cumulative
WHERE koi_disposition = 'CONFIRMED'
\end{lstlisting}

The name of the table is \texttt{cumulative} in the NASA Exoplanet Archive TAP service and so we use this naming. Finally, as this was for confirmed planets only we specify the Exoplanet Archive Disposition to be \texttt{"CONFIRMED"}.

For the eclipsing binaries, searching for rows with the disposition as "Eclipsing Binary" or "False Positive" was not sufficient as the first is not an option and the second includes multiple possible cases. In order to gather the data a second table was required. This is the Kepler Eclipsing Binaries table and it contains the KepIDs of all the EBs confirmed from the \textit{Kepler} mission. The table was read from the Kepler Eclipsing Binary Catalog webpage and after taking the KepIDs, another SQL query was applied, written out in Listing~\ref{lst:eb-query}. The list of KepIDs is saved into \texttt{kepid\_string} and we simply specify this in the query to pull only the EBs and their selected metadata columns. These catalogue queries defined the labelled objects and associated metadata, while the retrieval and preprocessing of the corresponding light curves was carried out in the data preparation stage.

\subsection{Data Preparation}

The overall process of downloading and preparing each light curve was done using the \textit{lightkurve} Python package \textbf{(GET CITATION)}. Each KepID was inputted into the library to collect its flux data. As \textit{Kepler} observations are divided into quarters\textbf{(Have I mentioned this properly?)}, multiple light-curve files can exist for a single target and thus we must stitch them all together. Next, all NaN values were removed, outliers beyond $5\sigma$ were dropped as well. In the same step the data was normalized so that flux values were placed on a common relative scale. Next, the time-series data was flattened which removed slow, long-term trends from the light curves while trying to preserve the shorter transit or eclipse events. This was done in the \textit{lightkurve} package by applying a Savitzky-Golay filter and dividing it out. The processed flux for each \textit{Kepler} object was then saved to a NumPy array.

To make the download process more manageable, the total batch was split into sub-batches of 200 KepID's. Every sub-batch was saved into a separate CSV file until all light curves are processed. Each finalized CSV file contained two columns: the KepID and the corresponding flux sequence. Since each KepID could produce multiple light curve chunks, it was important to keep them labelled for the modelling step. Through the process, if a KepID did not return a usable light curve, that object was skipped and recorded separately. KepIDs can be determined unusable if \textit{lightkurve} cannot find any data to download or the collected data could not be processed following the steps in this methodology. Overall \textbf{(How many total could not be downloaded?)} were skipped.

A total of \textbf{(Make sure)} 2745 confirmed exoplanets were pulled from the Kepler Exoplanet Archive catalogue. This same process was then repeated for the eclipsing binaries. The initial file collected from NASA had 2878 \textbf{(Also check this one)} catalogued eclipsing binaries. The KepIDs are processed into sub-batches of 200 KepIDs and saved to CSV files just like the transits and include the same column data. After removing unusable downloads, the final processed sample contained \textbf{(check number)} confirmed exoplanet targets and \textbf{(check number)} catalogued eclipsing binary targets. An extra column needed to be added for the splitting of the binary cases into shallow and deep categories. In order to do this, the entire light curve was scanned to extract the 100 smallest data points and takes the median of the list. This is to avoid outliers which could return a false dip. The median of these points was used then as an estimate of the minimum relative flux observed when the system is in total transit or eclipse.

After collection, the raw data and catalogue metadata needed to be converted into consistent formats suitable for the model and future evaluation. First, each input into the CNN model must be the same length and so we needed to determine how to standardize the length of each model input. We also wanted to expand the total number of training instances we could use which would increase the number of training samples available to the model. The method chosen was to split each light curve into fixed length segments of 4894 flux measurements. Given the time step of the \textit{Kepler} mission was 29.4 minutes, this means each chunk covers a length of $\sim 100$ days. Many targets can be split into three or more of these chunks increasing the total instances to \textbf{(How many?)}. Afterwards, the chunks are saved into new CSV files, again with each containing 200 total \textit{Kepler} objects. 

When preparing the model inputs, the saved flux sequences were read from the processed CSV files and converted into NumPy arrays. These arrays were then stacked so that each row represented one fixed length light curve sample. The CNN input itself used the processed flux arrays, while the catalogue KepID was retained to link each sample back to its metadata. For the purpose of further analysis, the remaining catalogue columns in Table~\ref{tab:kep_query_cols} were retained for later analysis. 

For the multi-class version of the experiment, a split threshold needed to be determined between the deep and shallow eclipsing binary cases. Using the binary model misclassification results and depth distribution, a practical separation was determined such that any chunk with an estimated dip $\geq 0.01$ \textbf{(Check this value)} is considered a deep binary. The classification of shallow or deep was saved to each eclipsing binary chunk.

Another new column was needed and that was a calculated signal to noise estimate of each instance. While Kepler does provide a column, some rows especially in the eclipsing binary cases were missing values. In order to assign an SNR estimate to as many test cases as possible, a simple formula was applied and shown in Equation~\ref{eq:snr_calc}. As this quantity was calculated directly from the available light curves, this value allowed each test instance to have an assigned relative SNR estimate. NumPy was used for the standard deviation and the transit depth values, the result for each instance was added to the updated table. 

\begin{align}
    \text{SNR} = \frac{\text{Transit Depth}}{\text{Standard Deviation}} \label{eq:snr_calc}
\end{align}

The light curve samples were split into training, validation, and testing sets. First we make sure there were no overlaps in the exoplanet and eclipsing binary datasets. While this should not happen it was a good precaution to make sure no data was repeated in both classes. This could reduce the reliability of learned classification boundary. Next, training works best when the data set of trained on exoplanets and eclipsing binaries is the same. This gives equal importance to learning the patterns in each class. Thus the data sets are made to match the size of the smaller one. This takes the eclipsing binary dataset from \textbf{(How many total?)} to \textbf{(How many total?)}. 

Now the data was ready to be split into the different sets. However it was very important to manage how the instances are split. For one KepID, we cannot have one of its chunks in the training set, while another was in the validation or test set. This would be unfair to the model as it will likely recognize target specific features giving a false boost in the final algorithm's score. This would lead to data leakage and would be notable in the validation results. Thus to avoid this, we split the data into the three sets not by individual rows but by KepIDs.

The pipeline split the data using a 80/10/10 division for training, validation, and testing. Thus in preparation, the data assigned 80\% of the KepIDs and saved them to the training set. The remaining 20\% was split in half to give 10\% to validation and 10\% to testing. Instead of taking the first 80\% of instances, the unique KepIDs were shuffles using a fixed random seed. This allows us to randomize which targets end up being used for training, validation, and testing while maintaining the rule of keeping associated KepIDs in the same set.  

This splitting process was done separately for the transit and eclipsing binary data giving a training, validation, and testing data set for both classes. Before concatenating the two classes, the arrays of the labels needed to be made. Class 0 was the label given to all confirmed eclipsing binaries while for confirmed transits they were labelled class 1. The training, validation, and test flux arrays and class labels were combined giving the completed sets of data and their outputs. In the case of the multi-class model, all steps are the same however the eclipsing binary data was split to its shallow and deep categories. Then transits were class 0, shallow binaries were class 1 and class 2 was for the deep eclipsing binaries. The three classes were balanced by selecting the same number of transit, shallow eclipsing, and deep eclipsing groups for the training. For both models, each of the three sets are given one last shuffle to avoid ordering the samples by class. Once more, a set seed was used to maintain reproducibility.  

The final training, validation, and test datasets are saved separately into three compressed NumPy files. Each file contains the light-curve input arrays, the associated class labels, and the KepIDs needed for later error analysis.

\subsection{Model}

The model was designed to classify one-dimensional Kepler light curves into two classes: confirmed transiting exoplanets and eclipsing binaries. Features such as transit or eclipse depth, dip shape, and repeated structures made a convolutional neural network (CNN) an appropriate model for research. The CNN scanned across the time axis looking for local patterns and shapes to determine what system created the overall data. Once the network's learned filters finished passing over the data it returned an informed estimate of whether the morphology was more consistent with a planetary transit or an eclipsing binary. As there are only two classes, the model outputs a binary classification value for transit and eclipsing binary predictions respectively.

A second multiclass version of the CNN was also trained to create the distinction between shallow and deep eclipsing binaries. Using the same process as the binary CNN, most layers are unchanged. The only required change was the final output layer which now gives 3 values representing the models probability estimate for each of the 3 cases. 

To structure the CNN, the TensorFlow and Keras Python libraries were used. As CNNs are structured as layers, these libraries were chosen because they provide a clear framework for defining sequential neural networks. Table~\ref{tab:layer_order} shows the finalized order of layers used in the neural network. This order follows a standard one-dimensional CNN architecture.

The input layer receives a stacked NumPy array with each of the light curves being analysed. From here each light curve was put into a one-dimensional convolutional layer which runs a kernel of set size over the flux time series. The learned filters are applied through the data along the time-axis, updating their weights through back propagation during the training. The goal of the filters was to search for local patterns in the light curve. These kernels can learn features associated with transit or eclipse dips, ingress or egress shape, as well as symmetry or asymmetry around dips. Multiple filters are learned and updated at once allowing the network to detect several features at a time. By utilizing multiple layers for convolution, simple features can be combined to detect more complex patterns.

Rectified Linear Units (ReLU) activations were used to introduce non-linearity which helped the model learn more complex patterns. In addition, ReLU activations helped reduce vanishing gradient effects during the iterative learning process. After the activation function of the convolutional layers, a batch normalization layer was applied. This standardized the intermediate activation results while training was occurring. Thus the next layer received values more appropriately scaled. This was done to reduce sensitivity to learning rate decisions. The next layers were max-pooling which took the largest element within a local window and retains it while discarding the rest. This lowered the computational load on the algorithm as it learned while retaining the important information. Following this a dropout layer was applied. These randomly disabled some neurons in the layer during training and reactivated them during evaluation. This was done to keep the network from relying too heavily on one path or unit. 

A final pooling layer was needed near the end of the network in order to convert the learned feature maps into a compact representation. Global pooling was then used to reduce each feature map by keeping the most strongly detected version of each learned pattern and converts them into a compact vector to prepare for the dense layers. The dense layers combined the information from the convolutional layers and learn combinations of features that separate the two classes. The final dense layer was chosen based on the type of model being trained. For the binary case, this output layer contained one neuron with a sigmoid activation function to produce the classification score. This score sits between 0 and 1 which was then converted to a binary number. Scores below the threshold returned 0 for eclipsing binary predictions while any scores above it assigned 1 for transit exoplanets predictions. The distance of this score from the classification threshold was used as a measure of model confidence using Equation~\ref{eq:confidence} below, where $p$ is the sigmoid classification score. 

As for the multiclass case, there were three output neurons with each representing one of the classifications. The activation chosen was softmax which gives a probability for each final neuron, and the loss function was sparse categorical cross-entropy. As the labels are given as 0, 1, 2 and not as one-hot vectors, this was the best choice for classifying our results. The confidence value is simply taken as the output neuron with the largest recorded probability.

\begin{align}
    \text{confidence} = \max{(p, 1-p)}\label{eq:confidence}
\end{align}

The above training process was repeated over several epochs with a backpropagation step after each mini batch. For the backpropagation, an optimizer was required and for this paper the Adam optimizer was used. Adam was chosen as it adjusts update sizes for different network weights making it more stable than more basic choices. Alongside the optimizer was the learning rate which controlled how large each update step was. A choice of \textbf{(What number?)} was used to avoid too big steps and too small updates. Alongside this, a weight decay value of \textbf{(What number?)} was chosen. This value was used for regularization to discourage overly large weights in the filter, preventing over-fitting.

The loss function was needed to compare the results of each training iteration with the real answers and measures the difference between predicted scores and true labels. As the classification was binary, binary cross-entropy was the chosen loss function as it works well with the sigmoid classification score. For the multiclass CNN, sparse categorical cross-entropy was used instead because labels were stored as integer values. For both models, as the total training data set was large, a random selection of $32$ light curve predictions were used to determine the weight updates during backpropagation. The model was trained for up to 10 epochs. Early stopping was used to monitor the validation loss during training and restore the model weights from the best validation epoch.

Upon completing the training epochs, the weights and model architecture were saved to a Keras model file which can be loaded and applied to validation or test light curves prepared in the same format. As well, the history of the training was saved into a JSON file. This can then be used to inspect how the model performed at each epoch in its training process. Several metrics were chosen to record in the learning process. Accuracy was recorded as the fraction of correctly classified samples. As well, the loss was recorded to show the prediction error during training. Both have results recorded at each epoch for both the training data and validation data. The training loss results were taken into account for updating the model and the validation metrics were recorded to allow for later comparison of the model's performance.

Several other metrics are recorded after training. The finalized models were evaluated on the test set. The binary model had a file saved holding the accuracy, precision, recall, F1 score, and ROC AUC. For the multiclass model, the accuracy, averaged precision, recall, and F1 score were saved. These results can then be monitored to understand more concretely what the model was good at and where it struggles.

\subsubsection{Random Forest Model}

To provide a comparison to the CNN model, a random forest model was used. It serves as a baseline and simpler process which helps to test whether the CNN is learning extra time-series shape information.

The random forest did not use the direct full light curves but instead used features of the individual chunks. From the chunk data, the mean, standard deviation, minimum, and maximum of the flux data were extracted as input features. As well the estimated chunk depth was added to the observed features. Metadata from the Kepler archive were not applied to the model as this info comes from processed data and would not be a fair comparison to the CNN. 

This model was trained where the prepared training and validation sets were combined to become the full training set with the test set being kept untouched. The same metrics as the convolutional neural network were collected and used for later comparison between the two models. This process was also applied to the multiclass case. 

\subsubsection{Error Analysis}

To further analyse the CNN, all misclassified light curves were saved in a compressed NumPy \texttt{.npz} file. Their KepID, flux input array, true class, predicted class, and confidence value calculated from the sigmoid score. This was then split into all false positives and all false negatives to understand better the limitations of the current model. 

Standard classification metrics quantify the overall performance of the model. However, they cannot explain what information or instances the model misclassified. Thus, the incorrect results needed to be saved into a separate dataset. To do so the test results were compared to the true classifications and those which did not match were saved into a compressed NumPy file. For the binary model, false positives were saved as instances which were predicted to be transits but are labelled eclipsing binaries samples while false negatives were for true transits predicted to be eclipsing binaries. 

Inside the saved file several arrays of information are kept. First the data was split into the false positives and false negatives. Within each subset, the true and predicted class are recorded along with the KepID. Keeping this identifier allows for analysing specific light curves more thoroughly. The flux data was also saved in the file for quicker access. The sigmoid score was useful as it gives the confidence value which makes it easier to understand if the model believed its prediction was close to or far from the classification threshold. As this was binary classification it was possible for the model to provide uncertain predictions. 

One important analysis to focus on the confidence of the model's predictions. The misclassified results were saved into subcategories of low, medium, and high confidence. As confidence can be a minimum of 0.5 and a maximum of 1.0, low-confidence cases were defined as in the 0.5 to 0.75 range, medium was between 0.75 to 0.85 and high was 0.85+. With this split now the results can be analysed to see trends associated with systematic model errors rather than isolated mistakes. By looking over the properties of Table~\ref{tab:kep_query_cols} split by the confidence this was possible.
